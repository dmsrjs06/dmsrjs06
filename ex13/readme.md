# 과제 13: 병합 정렬과 퀵 정렬의 성능 비교

병합 정렬(Merge Sort)과 퀵 정렬(피벗: First / Random / Median-of-Three)의 **비교 횟수, 실행시간, 추가 메모리 사용량**을 측정하고 비교했습니다.

- 소스: `MergeQuick.c` / 실행 로그: `result13.txt`
- 빌드·실행: `gcc -O2 -o MergeQuick MergeQuick.c -lm && ./MergeQuick`

## 1. 실험 및 측정 방법

| 항목 | 방법 |
|---|---|
| 데이터 | n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000, 값은 0~1,000,000 무작위 정수(중복 허용). 같은 원본의 복사본을 4가지 정렬에 제공 |
| 병합 정렬 | 하향식(top-down) 재귀. 임시 배열 1개를 정렬 시작 시 `malloc`, 끝나면 `free`. `a[i] <= a[j]`로 비교(안정 정렬). 병합 중 값 비교만 1회로 계산 |
| 퀵 정렬 | 과제 12와 동일한 분할·피벗 구현(Median-of-Three의 중앙값 결정 비교도 포함). 재귀 방식 |
| 비교 횟수 | 값끼리의 비교만 카운트(인덱스·종료 조건 검사, 난수 생성, 데이터 이동 제외). 본 표는 **크기당 원본 1개**로 측정. 보조로 20개 데이터 평균도 구함 |
| 실행시간 | 고해상도 타이머(Windows `QueryPerformanceCounter` / Linux `clock_gettime`)로 정렬 호출 직전~직후만 측정. 데이터 생성·복사·출력은 제외. 너무 짧아서 **같은 원본으로 200회 반복한 평균**(ms). 병합 정렬의 임시 배열 할당·해제 시간은 알고리즘의 일부이므로 포함 |
| 메모리 | 아래 3절 참고 |
| 검증 | 모든 실행에서 오름차순 여부와 원본과 같은 원소 집합인지 확인 → **전부 통과** |

## 3. 메모리 측정 방법과 계산 기준
원본 배열은 공통 비용이므로 제외하고, **정렬 중 추가로 필요한 메모리 = 추가 힙 메모리 + 최대 스택 사용량**으로 정의했습니다.
- **추가 힙**: 병합 정렬의 임시 배열 `n × sizeof(int) = 4n` Byte(n = 20,000이면 80,000). 퀵 정렬은 0.
- **최대 스택**: 재귀 함수가 호출될 때마다 지역변수의 주소를 기록해 **가장 낮은 주소**를 추적하고, 정렬을 시작한 지점의 주소와의 차이를 최대 스택 사용량으로 계산했습니다(실제 스택 프레임 크기를 반영하는 **실측**). 최대 재귀 깊이도 함께 기록했습니다(`result13.txt`의 Memory breakdown).
- 표의 메모리 = 추가 힙 + 최대 스택. 스택 프레임 크기는 컴파일러, 최적화 옵션, 플랫폼에 따라 달라지므로 **절대값보다 크기 변화의 경향**이 중요합니다(이 환경에서는 프레임 하나가 약 100 Byte).
- 측정 시에는 정렬 결과나 비교 횟수에 영향이 없도록, 시간 측정과는 별도의 실행에서 수행했습니다.

## 4. 분석

### 4.1 비교 횟수
- **병합 정렬이 모든 크기에서 가장 적은 비교**를 했습니다(n=20,000 평균 260,881회). 이는 이론식 `n·log₂n − 1.25n ≈ 260,754`와 거의 일치합니다. 병합 정렬은 항상 구간을 정확히 반으로 나누므로 입력에 상관없이 비교 횟수가 거의 같고, 한쪽이 먼저 소진되면 나머지는 비교 없이 복사하기 때문에 `n·log₂n`보다 약간 적습니다.
- **퀵 정렬(Median3)은 병합 정렬보다 약 30% 더 많은 비교**(339,870 vs 260,881), First/Random은 약 38% 더 많이 사용했습니다. 퀵 정렬은 피벗이 완벽한 중앙값이 아니라서 분할이 불균등하고, 그만큼 비교가 늘어납니다. 퀵 정렬의 이론 평균 `1.39·n·log₂n`, Median-of-Three `1.19·n·log₂n`와 실측(n·log₂n 대비 1.26, 1.19)이 맞습니다.
- 크기가 2배가 될 때 두 알고리즘 모두 비교 횟수가 약 2.1~2.3배로 늘어 **O(n log n)** 임을 확인했습니다.

### 4.2 퀵 정렬의 피벗 선택
- 비교 횟수는 **First ≈ Random**이고(무작위 데이터에서 첫 원소도 무작위 원소와 같기 때문), **Median-of-Three가 평균 5~6% 적습니다**(과제 12와 같은 결과). 크기당 1회인 본 표에서는 순위가 뒤바뀌는 크기가 있으므로(예: n=2,000의 First/Random/Median3 차이는 몇 백 회), 순위는 20회 평균(2.2절)을 근거로 해석했습니다.
- **시간은 Random이 가장 느렸습니다**(n=20,000에서 1.70ms vs First 1.31ms, Median3 1.28ms). 비교 횟수는 First와 같은데도 느린 이유는 분할마다 `rand()`를 2번 호출하는 비용이 있기 때문입니다(난수 생성은 비교 횟수에는 포함하지 않지만 실행시간에는 포함). 같은 프로그램을 4번 다시 실행해도 n=20,000에서 `First ≈ Median3 < Merge < Random` 순서가 유지되었습니다.
- 정렬된 입력(2.3절)에서는 **First가 12,507,498회**(약 n²/2)로 O(n²)이 되었고, 재귀 깊이가 n(5,000)까지 늘었습니다. Random·Median3는 입력과 무관하게 안정적이었습니다.

### 4.3 실행시간
- 병합 정렬은 비교는 가장 적었지만 **실행시간은 Quick(First/Median3)보다 느렸습니다.** n≥4,000에서 Merge/Quick(Median3) 시간 비율이 1.1~1.4배였고(n=20,000에서 1.27배), 반복 실행에서도 방향은 같았습니다(n=1,000~2,000은 측정값이 너무 작아 잡음이 커 비율이 들쭉날쭉하므로 해석에서 제외).
- 이유는 **비교 외의 작업량**입니다. 정수 비교 한 번은 매우 싸고, 시간은 데이터 이동·메모리 접근이 좌우합니다. 병합 정렬은 병합 때마다 원소를 임시 배열로 옮기고(`n`번) 다시 원래 배열로 복사하므로(`n`번), 약 `2·n·log₂n`번의 원소 이동과 임시 배열 `malloc/free`가 필요합니다. 퀵 정렬은 제자리(in-place)에서 필요한 원소만 교환하고 순차 접근이라 캐시 효율도 좋습니다.
- 시간은 모든 알고리즘에서 크기가 2배일 때 약 2.1~2.5배(n ≥ 4,000)로 증가해 n log n을 따릅니다.

### 4.4 메모리 사용량
- 병합 정렬은 크기에 **비례**해서 늘었습니다(5,240 → 81,720 Byte, n이 20배일 때 약 15.6배). 대부분이 임시 배열 `4n` Byte이고 스택은 1.2~1.7KB뿐입니다(재귀 깊이가 `log₂n`이라 11 → 16).
- 퀵 정렬은 추가 배열이 없고 스택만 사용해 **약 1.8~3.8KB로 거의 일정**합니다(n=20,000에서 Median3 2,552 Byte). 병합 정렬의 약 **21~32분의 1** 수준입니다(81,720 대 2,552~3,800).
- 단, 퀵 정렬의 스택은 **최악의 경우 n까지** 커집니다. 정렬된 입력에서 First는 재귀 깊이가 5,000, 스택이 **480,153 Byte**(병합 정렬 전체 약 21.5KB의 22배)였습니다. 이 비율(프레임당 약 96 Byte)이라면 n=20,000의 정렬 입력은 약 1.9MB가 필요해, 일반적인 기본 스택 크기(Windows 1MB)를 넘겨 **스택 오버플로**가 날 수 있습니다(n=20,000은 직접 실행하지 않은 추정).

### 4.5 시간·공간 복잡도

| | 병합 정렬 | 퀵 정렬 |
|---|---|---|
| 시간 (평균) | O(n log n) | O(n log n) |
| 시간 (최악) | **O(n log n)** (입력 무관) | **O(n²)** (First + 정렬된 입력: 12,507,498회) |
| 공간 | O(n) 임시 배열 + O(log n) 스택 | O(log n) 스택(평균), O(n)(최악) |
| 안정성 | 안정(`<=` 사용) | 불안정 |

## 5. 결론
- **비교 횟수**: 병합 정렬 < 퀵(Median3) < 퀵(First ≈ Random).
- **실행시간**: 이 실험에서는 퀵(First/Median3)이 병합 정렬보다 빨랐고(약 20~30%), 병합 정렬은 비교는 적지만 원소 복사와 임시 배열 때문에 느렸습니다. Random은 `rand()` 호출 비용 때문에 가장 느렸습니다.
- **메모리**: 퀵 정렬이 병합 정렬보다 압도적으로 적습니다(수십 분의 1). 하지만 피벗이 나쁘면(First + 정렬된 입력) 시간뿐 아니라 스택도 O(n)이 됩니다.
- 따라서 평균 성능·메모리가 중요하면 **Median-of-Three 퀵 정렬**, 최악 성능 보장과 안정성이 중요하면 **병합 정렬**이 적합합니다.

## 6. 한계
- 실행시간은 컴파일러 옵션·컴퓨터 환경에 따라 달라지며, n이 작을수록 잡음이 큽니다. 위 수치는 제 실행 환경 기준이므로 직접 실행한 값으로 표를 채워 제출하세요.
- 스택 사용량은 지역변수 주소로 측정한 값이라 프레임 크기가 환경에 따라 다릅니다.
- 병합 정렬은 하향식 구현 하나만 사용했고, 정렬된 입력 실험은 n=5,000 한 가지만 했습니다.
