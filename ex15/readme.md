# 과제 15: 퀵 정렬과 AVL 트리 정렬의 성능 비교

같은 무작위 데이터를 ① **퀵 정렬 + 정렬된 배열**, ② **AVL 트리**에 넣어 정렬한 뒤, 삽입·삭제를 n의 20%만큼 반복하면서 **총 수행시간, 비교 횟수, 데이터 이동 횟수, 메모리 사용량**을 비교했습니다.

- 소스: `QuickAVL.c` / 실행 로그: `result15.txt`
- 빌드·실행: `gcc -std=c11 -O2 -o QuickAVL QuickAVL.c && ./QuickAVL`
- 사용한 퀵 정렬 피벗: **Median-of-Three** (과제 12~14에서 비교 횟수가 가장 적었던 방법)

## 1. 구현 및 측정 기준

| 항목 | 내용 |
|---|---|
| 데이터 | n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000, 값은 0~1,000,000 무작위 정수(중복 허용). 두 방법에 같은 원본 사용 |
| 연산 | n의 20%(200 ~ 4,000회). 난수가 짝수면 삽입, 홀수면 삭제. 삽입·삭제할 값은 **별도의 새 난수**. 삭제 대상이 없으면 건너뜀. 연산 목록은 미리 만들어 **두 방법에 동일한 순서·값**을 적용 |
| 배열 삽입 | 선형 탐색으로 위치를 찾고 뒤 원소를 한 칸씩 뒤로 이동 |
| 배열 삭제 | 선형 탐색 후 삭제하고 뒤 원소를 한 칸씩 앞으로 이동. 중복이 있어도 한 개만 제거 |
| AVL 트리 | 노드에 `key, cnt(중복 횟수), height, left, right`. 중복 값은 `cnt`로 저장하고, 삭제 시 `cnt > 1`이면 `cnt`만 감소. 삽입·삭제 후 회전(LL/RR/LR/RL)으로 균형 복구. 노드가 둘인 삭제는 중위 후속자로 대체 |
| 비교 횟수 | 데이터 값끼리의 3방향 비교(`<`, `==`, `>` 한 번)를 **1회**로 계산. 배열 탐색은 첫 `a[i] >= v`에서 멈춤. 균형 인수 계산, 인덱스·종료 조건 검사는 제외. 퀵 정렬의 피벗 선택 비교는 포함 |
| 이동 횟수 | 값의 복사·대입을 1회로 계산. 퀵 정렬의 교환은 3회, 배열의 한 칸 이동과 삽입값 저장은 각 1회. AVL은 **노드 생성 시 키 저장 1회**, 노드가 둘인 삭제에서 후속자의 **키·`cnt` 복사 2회**. 포인터 연결 변경(회전 등)과 `cnt` 증감은 제외 |
| 총 수행시간 | 정렬 시작부터 모든 삽입·삭제 종료까지(C11 `timespec_get`). 같은 데이터로 **20회 반복한 평균**. 원본 배열 복사, 연산 난수 생성, 트리 해제, 결과 출력은 제외. AVL의 `malloc`은 알고리즘의 일부로 포함 |
| 메모리 | 아래 4절 참고 |
| 검증 | 모든 크기·모드에서 ① 정렬 후 배열 오름차순 ② 정렬 직후 AVL 중위 순회 = 정렬된 원본 ③ 모든 연산 후 AVL 중위 순회(중복 펼침) = 배열 ④ AVL 높이·균형 조건 ⑤ 최종 개수 일치 → **모두 통과** |

## 3. 분석

### 3.1 총 수행시간과 비교 횟수
- **비교 횟수는 AVL이 압도적으로 적습니다.** n=20,000에서 **321,131 vs 41,746,420으로 약 130배** 차이입니다. 이유는 **삽입·삭제 단계**입니다. 배열은 위치를 찾으려고 선형 탐색을 하므로 연산 한 번에 평균 `크기/2`(약 1만 번)의 비교가 필요하고(41,401,246 ÷ 4,000회 ≈ 10,350), AVL은 트리 높이(약 `log₂n`)만큼만 비교합니다(58,590 ÷ 4,000회 ≈ 14.6).
- **정렬 단계만 보면 두 방법이 비슷합니다.** 퀵 정렬 345,174, AVL 구성 262,541(약 `n·log₂n`)로 모두 O(n log n)입니다. 즉 차이는 정렬 자체가 아니라 **정렬 이후의 유지·갱신 비용**에서 생깁니다.
- **총 수행시간은 n ≥ 2,000에서 AVL이 빠릅니다.** n=20,000에서 약 5.2ms vs 30.7ms(**약 6배**)입니다. 같은 프로그램을 5번 더 실행해도 n=20,000에서 AVL은 4.6~5.4ms, Quick+배열은 29.9~36.8ms로 방향이 일정했습니다.
- **시간 차이(6배)가 비교 횟수 차이(130배)보다 훨씬 작은 이유**는 "비교 1회의 비용"이 다르기 때문입니다. 배열의 선형 탐색과 한 칸씩 이동은 연속된 메모리를 순차적으로 훑어서 캐시와 프리페치에 매우 유리하고 반복 한 번이 아주 쌉니다. 반면 AVL은 노드마다 `malloc`, 포인터 따라가기(캐시 미스 가능), 회전·높이 갱신 비용이 붙습니다. 그래서 비교 횟수만으로 시간을 예측할 수는 없습니다.
- **n = 1,000에서는 사실상 동점**입니다(0.123 vs 0.115ms). 반복 실행에서 AVL이 빠른 경우와 느린 경우가 섞여 나왔습니다(AVL 0.108~0.160ms, Quick 0.103~0.281ms). 데이터가 작으면 연산당 탐색·이동량이 적어 배열의 단순함이 AVL의 로그 이점을 상쇄하기 때문입니다.

### 3.2 데이터 이동 횟수
- 배열은 삽입·삭제마다 **뒤쪽 원소를 모두 밀어야** 해서 이동이 `n`에 비례합니다. n=20,000에서 연산 단계의 이동이 **21,410,175회**(연산 1회당 평균 약 5,350회)로, AVL의 **1,970회**와 비교하면 **약 1만 배**입니다(전체로는 21,628,542 vs 21,786, 약 1,000배).
- AVL의 이동은 **노드를 새로 만들 때 키를 저장하는 1회**가 대부분입니다. 회전과 균형 복구는 포인터 연결만 바꾸므로 이동에 포함되지 않습니다. 정렬 단계도 AVL은 19,816회(원소 수에 가까움)인데, 퀵 정렬은 교환(3회 단위) 때문에 218,367회입니다. 중복이 있으면 `cnt`만 늘어 이동이 없어서 19,816은 n(20,000)보다 약간 작습니다.
- 이것이 두 구조의 핵심 차이입니다. **배열은 "순서 = 물리적 위치"** 이므로 중간 삽입·삭제가 O(n)이고, **트리는 "순서 = 포인터 연결"** 이라 삽입·삭제 시 연결만 바꾸면 되어 O(log n)입니다.

### 3.3 메모리 사용량
- **배열이 훨씬 적습니다.** n=20,000에서 **90,653 vs 695,855 Byte(AVL이 약 7.7배)**. 배열은 원소당 4 Byte(`int`)이지만, AVL 노드는 `key(4) + cnt(4) + height(4) + 정렬 패딩(4) + 포인터 2개(16) = 32 Byte`로 원소당 8배의 공간이 듭니다. 값 외의 대부분(약 87%)이 포인터와 균형 정보 같은 구조 오버헤드입니다.
- 배열의 메모리는 약 88KB(최대 개수 × 4) + 퀵 정렬 스택 약 3KB입니다. AVL은 거의 전부가 노드 메모리이고, 재귀 스택은 트리 높이(약 20) 정도의 프레임이라 노드 메모리에 비하면 매우 작습니다.
- 참고로 실제 `malloc`은 노드마다 관리용 헤더(보통 8~16 Byte)가 붙지만 이번 측정에는 포함하지 않았으므로, 실제 AVL 메모리는 위 값보다 더 클 것입니다(추정).

### 3.4 데이터 크기 증가에 따른 변화

| n이 2배 → | 배열 비교 | 배열 이동 | AVL 비교 | AVL 이동 |
|---|---|---|---|---|
| 1,000→2,000 | ×3.6 | ×4.4 | ×2.2 | ×2.0 |
| 2,000→4,000 | ×3.8 | ×3.5 | ×2.2 | ×2.0 |
| 4,000→8,000 | ×4.0 | ×4.0 | ×2.2 | ×2.0 |
| 8,000→16,000 | ×4.0 | ×4.0 | ×2.2 | ×2.0 |

- **배열 방식은 n이 2배가 될 때 비교·이동이 약 4배**가 됩니다. n이 2배이면 연산 횟수(n의 20%)도 2배이고, 연산마다 비용(`크기/2`)도 2배가 되기 때문에 전체가 **O(n²)** 입니다. 시간도 같은 경향입니다(4,000→8,000→16,000에서 ×3.3, ×4.7).
- **AVL은 약 2.2배**로 `n log n`에 가깝게 증가합니다. 이동은 거의 n에 비례(2배)합니다. 시간도 n=2,000 이후 2배당 약 2.3~2.5배로 증가했습니다.
- 그 결과 **n이 클수록 AVL의 시간 우위가 커졌습니다**(시간 비율: n=2,000 약 1.4배 → n=4,000 약 2.3배 → n=8,000 약 3.3배 → n=16,000 약 6.3배 → n=20,000 약 5.9배, 마지막 둘은 잡음 범위).

## 4. 메모리 측정 방법과 계산 기준
정렬과 삽입·삭제를 하는 동안 **필요한 최대 크기**를 기준으로 계산했습니다.
- **Quick+배열**: `(실행 중 최대 원소 수) × sizeof(int)` + 퀵 정렬 재귀 스택. 삽입으로 배열이 커질 수 있으므로 최대 원소 수를 기록했습니다.
- **AVL**: `(실행 중 최대 노드 수) × sizeof(Node)`(= 32 Byte, 64비트 기준) + 삽입·삭제 재귀 스택. 중복 값은 노드를 새로 만들지 않고 `cnt`만 늘리므로 노드 수는 서로 다른 값의 개수입니다.
- **스택**: 재귀 함수에서 지역변수의 주소를 기록해 가장 낮은 주소와 시작 주소의 차이로 계산한 **실측값**입니다(과제 13, 14와 같은 방법). 시간 측정과는 별도의 실행에서 측정했습니다.
- 노드 크기(32 Byte)는 컴파일러·플랫폼(32/64비트)에 따라 달라지므로 절대값보다 구조적 차이(원소당 4 Byte vs 32 Byte)를 봐야 합니다.

## 5. 보충 실험: 삭제 값을 기존 데이터에서 선택
과제 규칙대로 하면 삭제가 거의 일어나지 않으므로, 삭제할 값을 **원본 데이터에서 무작위로 골라** 삭제가 실제로 발생하게 만든 실험입니다(삽입 값은 새 난수, 연산 순서는 두 방법 동일).

| n | 삭제 성공 / 시도 | 방법 | 시간(ms) | 비교 | 이동 | 메모리(Byte) |
|---:|---|---|---:|---:|---:|---:|
| 4,000 | 379 / 397 | Quick+배열 | 1.3554 | 1,644,757 | 1,626,567 | 18,301 |
| | | AVL | 0.6576 | 52,224 | 4,761 | 130,079 |
| 20,000 | 1,835 / 1,935 | Quick+배열 | 30.8623 | 40,651,232 | 39,281,026 | 83,909 |
| | | AVL | 4.5920 | 318,752 | 23,420 | 643,135 |

- 삭제가 실제로 일어나도 결론은 같습니다. n=20,000에서 **비교 약 130배, 이동 약 1,700배, 시간 약 6.7배** AVL이 유리합니다. 배열 방식은 삭제할 때도 `선형 탐색 + 뒤의 모든 원소를 앞으로 이동`이 필요하기 때문입니다.
- AVL의 삭제는 이동이 거의 없고(노드가 둘인 경우 후속자 값·`cnt` 복사 2회), 회전은 포인터만 바꾸므로 이동에 포함되지 않습니다.
- (참고) 보충 실험의 최종 개수는 두 방법이 서로 일치했습니다(예: n=20,000에서 20,230).

## 6. 결론: 삽입·삭제가 반복되는 환경에서는 AVL 트리가 유리
- **이유**: 정렬된 배열은 순서를 물리적 위치로 표현하므로 삽입·삭제마다 위치 탐색 O(n) + 원소 이동 O(n)이 필요합니다. AVL 트리는 높이를 `O(log n)`으로 유지하면서 탐색·삽입·삭제를 모두 O(log n)에 처리하고, 이동 없이 포인터만 바꿉니다. 이번 실험에서 n=20,000일 때 비교 약 130배, 이동 약 1,000배, 시간 약 6배의 차이로 확인했습니다.
- **배열이 나은 경우**: 메모리가 중요할 때(원소당 4 vs 32 Byte, 약 7.7배 차이), 데이터가 작거나(n=1,000에서는 시간이 비슷), 정렬 후 조회·순회가 대부분이고 갱신이 드문 경우. 배열은 인덱스 접근 O(1), 연속 메모리로 인한 캐시 효율이라는 장점이 있습니다.
- 정리하면, **갱신이 잦고 데이터가 크면 AVL 트리, 메모리·단순함·조회 위주면 정렬된 배열**이 적합합니다.

## 7. 한계
- 실행시간은 컴파일러 옵션·컴퓨터 환경에 따라 달라지고 n이 작을수록 잡음이 큽니다. 위 시간 값은 제 환경 기준이므로 **직접 실행한 값으로 표를 채워 제출**하세요(비교·이동 횟수는 `rand()` 구현이 같다면 동일합니다).
- 총 수행시간만 측정했고 정렬 단계와 삽입·삭제 단계의 시간은 따로 나누지 않았습니다(비교·이동은 단계별로 분해).
- 삽입·삭제 연산 목록은 크기당 한 번만 생성했으며, 연산 목록을 바꾼 반복 측정은 하지 않았습니다.
- `malloc` 헤더는 메모리에 포함하지 않았습니다.
