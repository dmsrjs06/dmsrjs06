# 과제-06: 순차 탐색, 이진 탐색 트리(BST)와 AVL 트리의 성능 비교

## 1. 프로그램 개요

이 과제는 0~1000 사이의 정수 100개를 임의로 생성(같은 값이 여러 번
나올 수 있음)하여, 발생 순서 그대로 배열(중복 값은 제외하고 저장), BST,
AVL 트리에 각각 삽입을 시도한다. 세 자료구조는 항상 같은 순서로 같은 값을
처리하므로, 처리가 끝나면 세 자료구조에는 서로 같은 집합의 값이 저장된다.
이어서 0~1000 사이의 정수 50개를 탐색 대상으로 추가 생성하여 순차 탐색,
BST 탐색, AVL 탐색을 각각 수행하고 비교 횟수를 측정한다.

- 비교 횟수 정의: 배열은 중복 확인을 위해 기존 원소와 비교할 때마다 1회,
  BST/AVL은 삽입 위치(또는 중복 여부)를 찾기 위해 노드 값과 비교할 때마다
  1회로 계산한다. AVL의 높이 계산·balance factor 확인·회전 여부 판단에
  쓰이는 비교는 포함하지 않는다(코드에서도 이 부분은 별도의 비교 카운터를
  건드리지 않도록 분리했다).
- 트리의 높이는 노드 수 기준으로 정의한다(빈 트리 = 0, 루트만 있으면 = 1).
- 컴파일: `gcc -Wall -o CompareAVL CompareAVL.c`
- 실행: `./CompareAVL` (매 실행마다 `srand(time(NULL))`로 난수를 새로
  생성하므로 결과는 실행마다 달라질 수 있다.)
- 구현 검증: AVL 삽입/회전 로직만 따로 떼어 2,000회 무작위 삽입 시험을
  수행했고, 모든 노드의 balance factor가 항상 [-1, 1] 범위 안에 있고
  (균형 조건 유지), BST 순서 조건을 만족하며, 삽입된 값의 개수와 트리의
  노드 개수가 항상 일치함을 확인했다.

아래 분석은 실제로 한 번 실행한 결과(`avl_run_output.txt`)를 기준으로
작성하였다. 실행할 때마다 생성되는 난수가 다르므로 정확한 수치는 매번
달라지지만, 아래에서 설명하는 경향성(AVL 높이가 BST 높이보다 항상 작거나
같음, 생성 비용 대비 탐색 이득 등)은 거의 모든 실행에서 공통적으로
관찰된다.

## 3. 분석

### 3.1 BST와 AVL 트리의 높이가 서로 다른 이유

두 트리는 완전히 같은 98개의 값을, 완전히 같은 순서로 삽입받았다. 그런데도
BST의 높이는 13, AVL 트리의 높이는 8로 거의 두 배 가까이 차이가 난다.
이 차이는 오직 "삽입 후 균형을 맞추는 절차가 있는가"에서 비롯된다.

- BST는 새 값을 넣을 때 그 값이 들어갈 위치를 찾아 그대로 매달기만 한다.
  삽입 순서(난수가 나온 순서)에 따라 한쪽으로 치우친 경로가 우연히 여러
  개 생기면, 그 경로들이 그대로 트리의 높이를 늘린다. 98개의 값을 완전히
  균형 잡히게 배치했을 때의 이상적인 높이는 log2(98)+1 ≈ 8 정도인데, 실제
  BST 높이(13)는 이보다 훨씬 크다. 이는 무작위 순서로 삽입하더라도 특정
  구간에서 운이 나쁘면(예: 비슷한 크기의 값들이 연달아 한쪽 방향으로만
  삽입되는 경우) 그 부분이 긴 사슬처럼 이어질 수 있기 때문이다.
- AVL 트리는 새 값을 삽입한 직후 루트까지 거슬러 올라가며 각 노드의
  balance factor(왼쪽 서브트리 높이 − 오른쪽 서브트리 높이)를 확인하고,
  그 값이 -1~1 범위를 벗어나면 즉시 LL/RR/LR/RL 회전을 수행해 트리
  모양을 바로잡는다. 그 결과 어떤 순서로 값이 들어오더라도 높이가 항상
  log2(n) 수준으로 유지된다. 실제로 AVL 높이(8)는 이상적인 높이(약 8)와
  거의 일치한다.

즉 BST는 "운이 좋으면" 균형 잡힌 트리가 되지만 그 균형을 보장하는 장치가
없고, AVL은 매 삽입마다 스스로 균형을 복구하는 장치(회전)를 갖고 있다는
점이 높이 차이의 근본 원인이다.

### 3.2 트리의 높이가 탐색 비교 횟수에 미치는 영향

BST/AVL 탐색은 루트에서 시작해 한 단계씩 왼쪽 또는 오른쪽으로 내려가며
값을 비교하므로, 어떤 값을 찾기 위해 필요한 최대 비교 횟수는 그 값이 있는
노드의 깊이(또는 트리의 높이)로 결정된다. 측정 결과에서도 이 관계가
그대로 드러난다.

- BST 탐색 평균 비교 횟수(8.10)는 BST 높이(13)보다는 작지만, AVL 탐색
  평균(6.70)보다는 뚜렷하게 크다. 트리 높이가 13인 BST에서는 운이 나쁜
  경로를 타면 최대 13번까지 비교해야 할 수 있는 반면, 높이가 8인 AVL
  트리에서는 아무리 깊은 경로를 타도 최대 8번이면 끝난다.
- 평균적으로도 AVL 트리 쪽이 더 얕은 구조이므로, 같은 조건(찾는 값이 있든
  없든)에서 더 적은 횟수의 비교만으로 탐색이 끝난다. 이번 실행에서는 AVL
  탐색이 BST 탐색보다 평균적으로 약 17%(405 → 335) 더 적은 비교로
  끝났다.
- 두 트리 모두 순차 탐색(평균 95.74회)과 비교하면 압도적으로 적은
  비교 횟수를 보인다. 이는 데이터 100개 규모에서도 O(log n) 구조의
  이점이 이미 뚜렷하게 나타난다는 것을 보여준다.

결론적으로, 같은 수의 데이터를 담고 있더라도 "트리가 얼마나 균형
잡혀 있는가(=높이가 얼마나 낮은가)"가 탐색 성능을 직접 좌우한다.

### 3.3 세 자료구조의 생성 비용과 탐색 비용 비교

생성(삽입) 과정만 놓고 보면 AVL(540)이 BST(583)보다 오히려 비교 횟수가
약간 더 적게 나왔다. 언뜻 "AVL이 회전까지 수행하니 더 비쌀 것 같다"고
생각하기 쉽지만, 이 과제에서 측정하는 비교 횟수는 "저장된 값과 삽입하려는
값 사이의 비교"만 포함하고 회전 여부를 결정하는 balance factor 비교는
제외하기 때문에, 오히려 AVL이 삽입 중에도 트리를 얕게 유지하는 덕분에
새로운 값을 넣을 위치를 찾는 경로 자체가 BST보다 짧아지는 효과가 나타난다.
즉 회전에 드는 추가 비용(이 과제의 기준으로는 비교 횟수에 집계되지 않는
balance factor 계산·회전 연산)을 감수하는 대신, 그 다음 삽입부터는 더
얕은 트리 위에서 움직이게 되어 삽입 비교 횟수 자체도 줄어드는 선순환이
생긴다.

배열은 생성 과정에서만 4,853회의 비교가 필요했다. 이는 중복 검사를 위해
매번 현재까지 저장된 원소 전체(최대 98개)를 훑어야 할 수 있기 때문이며,
저장된 원소 수가 늘어날수록 한 번의 중복 검사 비용도 함께 커진다.

생성 비용과 탐색 비용을 모두 더해(구성 1회 + 탐색 50회) 비교하면 다음과
같다.

| 자료구조 | 생성 비용 | 탐색 50회 비용 | 합계 |
|---|---|---|---|
| 배열 | 4,853 | 4,787 | 9,640 |
| BST | 583 | 405 | 988 |
| AVL | 540 | 335 | 875 |

생성 비용까지 포함해도 AVL이 가장 적은 총 비교 횟수를 기록했고, 배열은
생성 단계에서부터 이미 BST/AVL의 생성+탐색을 합친 것보다 훨씬 많은
비교가 필요했다. 특히 배열은 "데이터를 쌓아 나가는 단계"부터 느리다는
점에서, 데이터가 많아지고 탐색을 자주 반복할수록 BST/AVL과의 격차는
더 벌어질 수밖에 없다. 반면 BST와 AVL을 비교하면, AVL은 삽입 시점에
드는 회전 비용(이 과제의 비교 횟수 기준으로는 보이지 않지만 실제로는
포인터 재배치 등의 추가 연산이 있다)을 감수하는 대신, 그 이후의 모든
탐색(그리고 이어지는 삽입)에서 더 얕아진 트리 덕분에 비용을 절감한다.
즉 한 번 만들어 놓고 여러 번 탐색·삽입을 반복하는 상황일수록 AVL
트리가 BST보다 유리하다.

## 4. 결론

- 같은 데이터를 담고 있어도 트리가 균형 잡혀 있는지에 따라 높이가 크게
  달라지며(이번 실행에서 BST 높이 13 vs AVL 높이 8), 높이는 곧 탐색에
  필요한 최대/평균 비교 횟수로 직결된다.
- AVL 트리는 삽입할 때마다 즉시 균형을 복구하므로 어떤 순서로 값이
  들어오든 높이가 항상 log2(n) 수준으로 유지되지만, BST는 삽입 순서에
  따라 운이 나쁘면 한쪽으로 치우쳐 높이가 크게 늘어날 수 있다.
- 탐색만 비교하면 AVL이 BST보다, 생성 비용까지 포함해도 AVL이 가장
  적은 총 비교 횟수를 기록했다. 배열(순차 탐색)은 생성과 탐색 모두에서
  BST/AVL과 자릿수 자체가 다른 비용을 보였다.
- 데이터 개수가 늘어나거나 탐색을 더 많이 반복할수록, 균형이 보장되는
  AVL 트리의 이점은 더욱 커질 것으로 예상된다.
