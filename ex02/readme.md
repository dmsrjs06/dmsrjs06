# 이진 트리(Binary Tree) 구현 방식 비교 분석 보고서

## 1. 메모리 사용량 비교

### 프로그램 실제 측정 결과 (실행 예시)
* **배열 구현 (Array):** 8 바이트 (최대 사용 인덱스 7 기준: 8 슬롯 × 1 바이트)
* **연결 구현 (Linked):** 120 바이트 (5 노드 × 24 바이트)
> **참고:** 배열은 포인터 없이 순수 데이터(1바이트)만 저장하지만, 연결 리스트는 데이터 외에 왼쪽/오른쪽 자식을 가리키는 포인터 2개(약 16바이트)와 패딩이 추가되어 노드당 통상 24바이트의 고정 오버헤드가 발생합니다.

### 트리 형태에 따른 이론적 메모리 분석
| 트리 형태 | 배열(Array) 구현 | 연결 자료구조(Linked) 구현 |
| :--- | :--- | :--- |
| **완전/포화 이진 트리** | $n+1$ 슬롯 (빈번한 빈 슬롯 없음) | $24n$ 바이트 |
| **일반 이진 트리** | 최대 $2^{h+1}$ 슬롯 (빈 슬롯 낭비 발생) | $24n$ 바이트 |
| **편향 이진 트리 ($n=10$ 예시)** | $2^{10} = 1024$ 슬롯 (실사용 10, 극심한 낭비) | $240$ 바이트 (형태 무관 고정) |

### 결론: 형태에 따른 메모리 효율성
* **완전/포화 트리는 배열이 유리:** 빈 인덱스가 거의 발생하지 않으므로 포인터 메모리를 아낄 수 있는 배열이 훨씬 경제적입니다.
* **편향 트리는 연결 리스트가 압도적 유리:** 트리가 한쪽으로 치우칠 경우 배열은 트리 높이 $h$에 따라 $O(2^h)$로 인덱스가 폭발하여 빈 슬롯 낭비가 심각해집니다. 반면 연결 구현은 형태와 무관하게 항상 노드 수에 비례하는 $O(n)$의 메모리만 안정적으로 사용합니다.

## 2. 노드 간 관계 (부모/자식/형제) 조회 효율

| 탐색 항목 | 배열(Array) 구현 | 연결 자료구조(Linked) 구현 |
| :--- | :--- | :--- |
| **탐색 원리** | 인덱스 산술 연산 | 노드 간 포인터 참조 |
| **자식 탐색** | $O(1)$ (왼쪽 $2i$, 오른쪽 $2i+1$) | $O(1)$ (좌우 포인터 즉시 이동) |
| **부모 탐색** | $O(1)$ ($i/2$, 소수점 버림) | $O(n)$ (루트 노드부터 하향식 재귀 탐색) |
| **형제 탐색** | $O(1)$ ($i$가 짝수면 $i+1$, 홀수면 $i-1$) | $O(n)$ (루트에서 부모를 먼저 찾아야 함) |

### 결론: 접근 방향에 따른 탐색 효율성
* **배열의 장점:** 현재 노드의 인덱스 $i$만 파악하면, 단순한 산술 연산만으로 부모, 자식, 형제 위치를 $O(1)$에 즉시 도출할 수 있습니다. 단, 문자를 통해 대상 노드의 인덱스를 알아내는 선행 검색 작업에는 $O(n)$이 소요됩니다.
* **연결 리스트의 한계:** 하향식(자식) 이동은 포인터로 빠르게 $O(1)$에 처리되지만, 상향식(부모)이나 수평적(형제) 이동을 위한 역방향 포인터가 없기 때문에 불가피하게 루트부터 다시 트리를 훑어야 하는 $O(n)$의 탐색 비용이 발생합니다.

---

## 3. 종합 요약
부모 및 형제 노드로의 거꾸로 된 접근이 빈번하게 요구되고 트리가 **완전 이진 트리** 형태를 유지한다면 **배열 구현**이 연산 속도와 메모리 양측에서 최적의 선택입니다. 

그러나 이 효율성은 트리가 완전에 가까울 때만 성립하며, 트리의 구조를 예측할 수 없거나 한쪽으로 치우칠(편향) 위험이 있는 일반적인 상황에서는 지수적인 메모리 낭비를 방지하기 위해 **연결 자료구조**를 채택하는 것이 정석입니다.
