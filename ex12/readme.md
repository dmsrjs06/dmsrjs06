# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교

퀵 정렬의 피벗을 **첫 번째 원소 / 무작위 원소 / 세 원소의 중앙값**으로 선택했을 때의 숫자 비교 횟수를 측정하고, 보너스로 재귀·반복(스택) 구현의 실행시간을 비교했습니다.

- 소스: `QuickCompare.c` / 실행 로그: `result12.txt`
- 빌드·실행: `gcc -O2 -o QuickCompare QuickCompare.c -lm && ./QuickCompare`

## 1. 실험 방법
- n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000, 값은 0~1,000,000 무작위 정수(중복 허용). Windows의 `rand()`는 최대 32767이라 두 번 호출해 30비트 난수로 만들었습니다.
- 각 크기에서 원본 1개를 만들어 **동일한 복사본**을 세 방법에 제공. 복사·생성은 측정 제외.
- 분할(partition)은 세 방법이 **완전히 동일**하며 피벗 선택 함수만 다릅니다. 선택한 피벗을 구간 맨 앞으로 옮긴 뒤 양쪽에서 스캔하는 방식이고, `a[i] < pivot`, `a[j] > pivot`을 엄격 부등호로 써서 중복 값도 올바르게 처리합니다.
- 비교 횟수: 분할 중 데이터와 피벗의 비교 + Median-of-Three에서 중앙값을 정하는 값 비교(세 값당 2~3회). 인덱스 범위 검사, 무작위 위치 생성, 데이터 교환은 제외.
- 모든 실행에서 ① 오름차순 ② 원본과 같은 원소 집합인지 확인했고 **전부 통과**했습니다.
- 본 실험은 크기당 1회라 편차가 있으므로, 같은 프로그램에서 **20회 반복 평균**도 구해 보조 근거로 사용했습니다.

## 3. 분석

### 3.1 크기 증가에 따른 변화
세 방법 모두 n이 2배가 될 때 비교 횟수가 약 **2.1~2.25배**로 늘었습니다(2배보다 조금 큰 이유는 `n·log n`의 log 항 때문). n²이었다면 4배가 되었을 것이므로 모두 **O(n log n)** 으로 증가합니다. 또 `비교 횟수/(n·log₂n)`이 1.2~1.28로 거의 일정하게 유지되어 이를 뒷받침합니다.

### 3.2 피벗 방법별 성능 차이
- **무작위 데이터에서는 First와 Random이 사실상 같았습니다.** 20회 평균에서 두 값의 차이는 모든 크기에서 약 ±4% 이내이고, 앞서는 쪽도 크기마다 바뀝니다. 크기당 1회인 본 실험에서도 First가 더 적은 크기(1,000, 2,000, 8,000, 16,000)와 Random이 더 적은 크기(4,000, 20,000)가 섞여 있습니다. 즉 한 번의 측정으로 둘의 우열을 말할 수는 없습니다.
- **Median-of-Three가 가장 적었습니다.** 본 실험의 6개 크기에서 4,000(57,078)과 20,000(329,071)처럼 대부분 최소였고(n = 1,000은 First가 근소하게 적음), 20회 평균에서는 모든 크기에서 First·Random보다 적었습니다. 감소폭은 n이 커질수록 0.8% → 5~6%로 커지는 경향입니다.
- 이는 `비교/(n·log₂n)`에서도 드러납니다. Median-3는 크기와 무관하게 약 **1.19**로 일정한 반면, First와 Random은 1.20 → 1.27 정도로 올라가는 경향이 있습니다.

### 3.3 왜 이런 차이가 생기는가
- 퀵 정렬의 비교 횟수는 **분할이 얼마나 균등한지**로 결정됩니다. 피벗이 구간의 중앙값에 가까울수록 두 부분이 비슷한 크기가 되어 재귀 깊이가 `log n`에 가까워지고, 각 단계에서 n번 정도의 비교로 정렬이 끝납니다.
- **First / Random**: 입력이 무작위라면 첫 원소도 "무작위 원소 한 개"와 통계적으로 같습니다. 그래서 둘의 성능이 같습니다. 이론상 평균 비교 횟수는 약 `2n·ln n ≈ 1.39·n·log₂n`이고, 실측 1.2~1.28이 이보다 낮은 이유는 작은 구간에서 비교가 이론식보다 적게 들기 때문(낮은 차수 항)으로 보입니다.
- **Median-of-Three**: 세 원소의 중앙값을 쓰면 극단적으로 치우친 피벗(가장 작거나 큰 값)이 나올 확률이 크게 줄어, 분할이 더 균등해집니다. 이론상 평균 비교는 약 `(12/7)·n·ln n ≈ 1.19·n·log₂n`으로 알려져 있는데, 실측 값 **1.19**와 정확히 일치합니다. 대신 매 분할마다 중앙값을 찾는 비교 2~3회가 추가되지만, 균등한 분할로 얻는 이득이 더 커서 총 비교가 줄었습니다.

### 3.4 입력이 정렬되어 있을 때 (보충 실험)
- First는 **12,507,498**회(= n(n+1)/2 ≈ 12,502,500 근처, **O(n²)**)로 폭발했습니다. 정렬된 배열의 첫 원소는 항상 최솟값이라 분할이 `0 : n-1`로 치우치고, 단계마다 원소가 1개씩만 줄기 때문입니다.
- Random은 89,287, Median-3는 63,630으로 정상 범위입니다. Random은 입력 순서와 무관하게 확률적으로 균등하고, Median-3는 정렬된 입력에서 가운데 원소가 정확히 중앙값이라 최적 분할이 됩니다.
- 따라서 **무작위 입력만 보면 First도 괜찮아 보이지만, 정렬된 입력 같은 현실적인 입력에서는 매우 위험합니다.**

### 3.5 어떤 방법이 효과적이었나
Median-of-Three가 무작위 입력에서 가장 적은 비교(평균 약 5~6% 감소)를 보였고, 정렬된 입력에서도 가장 적었습니다. Random은 입력에 상관없이 안정적이지만 이번 무작위 데이터에서는 First와 차이가 없었습니다. **효과 순서: Median-of-Three > Random ≈ First(무작위 입력), Median-3 > Random ≫ First(정렬 입력).**

## 4. 보너스: 재귀 vs 반복 퀵 정렬

- 구현: 반복 방식은 `(l, r)` 구간을 명시적 스택에 저장합니다. 오른쪽 구간을 먼저 push해 왼쪽이 먼저 처리되게 해서, 재귀와 **같은 순서·같은 분할·같은 피벗**을 사용합니다.
- 조건: n = 10,000, Median-of-Three, 같은 원본의 복사본, 300회 반복 평균. 복사·생성은 측정 제외. 실행 순서의 편향을 없애기 위해 매 반복마다 두 방법의 순서를 바꿔 측정했습니다. 단위는 ms(고해상도 타이머).

| 방법 | 평균 실행시간 (`result12.txt`) |
|---|---:|
| Recursive Quick Sort | 0.7609 ms |
| Iterative Quick Sort | 0.7029 ms |

- 두 구현의 비교 횟수는 **154,419로 동일**했고 정렬 결과 배열도 완전히 같았습니다(로직이 같음을 검증).
- **같은 프로그램을 여러 번 다시 실행해 보니** 재귀 0.90 / 반복 0.93, 재귀 0.74 / 반복 0.72, 재귀 0.68 / 반복 0.68 ms, 최적화 없이(-O0) 빌드해도 재귀 1.02 / 반복 1.03 ms 등으로 **어느 쪽이 빠른지가 실행마다 바뀌었습니다.** 즉 위 표의 차이(약 7%)는 측정 잡음 수준이며, **이 실험에서는 두 방법의 실행시간 차이가 없다**고 결론 내립니다.
- 이유: 두 방법의 연산량이 사실상 같기 때문입니다. 분할 작업(비교·교환)이 압도적으로 많고(약 15만 번 비교), 재귀는 함수 호출 시 스택 프레임을 만들고, 반복은 배열에 구간 값을 push/pop한다는 차이뿐인데, 호출 횟수(약 2만 번 수준)에 비해 이 오버헤드가 전체의 아주 작은 비율입니다. 또한 컴파일러가 재귀 호출을 최적화하고, 두 방식 모두 CPU 캐시에 잘 맞는 연속된 메모리를 다룹니다.
- 반복 방식의 실질적 장점은 속도가 아니라 **스택 깊이를 직접 제어**할 수 있다는 점입니다. 실제로 정렬된 입력에서 First 피벗의 재귀 깊이는 n에 달해 n이 크면 호출 스택 오버플로가 생길 수 있고(이 때문에 보충 실험을 n=5,000으로 제한), 반복 방식은 명시적 배열이라 이 위험을 다룰 수 있습니다(다만 이번 구현은 그런 최적화 없이 같은 순서로 처리).
