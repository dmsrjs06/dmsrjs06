# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

과제 13의 병합 정렬·퀵 정렬(First / Random / Median-of-Three)에 **힙 정렬(Heap Sort)**을 추가하여 **비교 횟수, 실행시간, 추가 메모리 사용량**을 비교했습니다.

- 소스: `HeapMergeQuick.c` / 실행 로그: `result14.txt`
- 빌드·실행: `gcc -O2 -o HeapMergeQuick HeapMergeQuick.c -lm && ./HeapMergeQuick`

## 1. 실험 및 측정 방법

| 항목 | 방법 |
|---|---|
| 데이터 | n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000, 값은 0~1,000,000 무작위 정수(중복 허용). 같은 원본의 복사본을 5가지 정렬에 제공 |
| 힙 정렬 | 입력 배열 자체를 최대 힙으로 사용(별도 힙 배열 없음), 재귀 없이 **반복문**으로 구현. ① `n/2-1`부터 0까지 sift-down으로 힙 구성 → ② 루트와 마지막 원소 교환 → 힙 크기 감소 후 sift-down → 반복 |
| 힙 정렬 비교 횟수 | sift-down에서 ⓐ 두 자식 중 큰 쪽을 고르는 비교 1회(자식이 둘일 때), ⓑ 선택한 자식과 내려보내는 값의 비교 1회. 힙 구성 + 정렬 단계의 값 비교를 모두 포함 |
| 병합/퀵 정렬 | 과제 13과 동일(병합: 하향식, 임시 배열 1개 / 퀵: 재귀, 분할 공통, 피벗 선택만 다름, Median-of-Three의 중앙값 비교도 카운트) |
| 비교 횟수 | 값끼리의 비교만 카운트(인덱스·종료 조건 검사, 난수 생성, 데이터 이동 제외). 본 표는 **크기당 원본 1개**, 보조로 20개 데이터 평균도 구함 |
| 실행시간 | 고해상도 타이머(Windows `QueryPerformanceCounter` / Linux `clock_gettime`)로 정렬 호출 직전~직후만 측정. 생성·복사·출력 제외. 같은 원본으로 **200회 반복한 평균**(ms). 병합 정렬의 임시 배열 `malloc`/`free`는 알고리즘의 일부로 포함 |
| 메모리 | 3절 참고 |
| 검증 | 모든 실행에서 오름차순 + 원본과 같은 원소 집합 여부 확인 → **전부 통과** |

## 3. 메모리 측정 방법과 계산 기준
원본 배열은 공통 비용이므로 제외하고, **정렬 중 추가 메모리 = 추가 힙 메모리 + 최대 스택 사용량**으로 정의했습니다(과제 13과 동일).
- **추가 힙**: 병합 정렬의 임시 배열 `4n` Byte(n=20,000이면 80,000). 힙 정렬·퀵 정렬은 0(힙 정렬의 힙은 입력 배열 자체).
- **최대 스택**: 각 함수 호출 시 지역변수의 주소를 기록해 **가장 낮은 주소**를 추적하고, 정렬 시작 지점과의 차이를 구했습니다(실제 스택 프레임을 반영한 실측). 최대 호출 깊이도 함께 기록했습니다(`result14.txt`의 Memory breakdown).
- 힙 정렬은 재귀가 없으므로 `heap_sort` → `sift_down` 두 함수의 프레임(깊이 2)과 보조 변수만 사용합니다. **296 Byte**에는 측정 시작 함수의 프레임 몫이 포함되어 있고, 이 기준 오차는 모든 알고리즘에 공통입니다.
- 스택 프레임 크기는 컴파일러·최적화·플랫폼에 따라 달라지므로 **절대값보다 크기에 따른 변화 경향**이 중요합니다.

## 4. 분석

### 4.1 비교 횟수
- **병합 정렬 < 퀵(Median3) < 퀵(First ≈ Random) < 힙 정렬** 순서가 모든 크기에서 같았습니다(20회 평균, n=20,000: 260,881 / 339,870 / 약 36만 / 510,734).
- **힙 정렬은 병합 정렬의 약 2배**(510,734 vs 260,881)입니다. sift-down에서 원소 하나를 한 층 내릴 때 비교가 **2번**(큰 자식 고르기 + 자식과 비교) 필요하기 때문입니다. 정렬 단계에서 `n−1`번 sift-down을 하고 각각 최대 `log₂n` 층까지 내려가므로 약 `2·n·log₂n`이 되며, 실측 `n·log₂n` 대비 1.69 → 1.79로 이 값(2)을 향해 서서히 올라갑니다(낮은 차수 항 때문에 2보다 작음).
- 병합 정렬은 항상 구간을 정확히 반으로 나누고 한쪽이 먼저 소진되면 비교를 멈추므로 `n·log₂n`보다 조금 적습니다(0.87~0.91). 퀵 정렬은 분할이 불균등한 만큼 비교가 늘어납니다(1.19~1.27).
- n이 2배가 될 때 모든 알고리즘의 비교가 약 2.1~2.3배로 늘어 **O(n log n)** 입니다.

### 4.2 퀵 정렬의 피벗 선택
- 20회 평균에서 **Median-of-Three가 First·Random보다 약 5~6% 적고**, First와 Random은 거의 같습니다(무작위 데이터에서는 첫 원소도 무작위 원소와 통계적으로 같기 때문). 크기당 1회인 본 표에서는 순위가 뒤바뀌는 크기가 있으므로(예: n=2,000은 차이가 수백 회) 순위는 평균으로 판단했습니다.
- 시간은 **Random이 느린 편**입니다. 비교 횟수는 First와 같은데도 분할마다 `rand()`를 호출하는 비용(비교 횟수에는 미포함)이 붙기 때문입니다.
- 정렬된 입력(2.3절)에서 First는 12,507,498회(≈ n²/2)로 **O(n²)** 이 되고 스택도 약 480KB(재귀 깊이 5,000)로 폭증했습니다. Random·Median3는 입력에 영향받지 않았습니다.

### 4.3 실행시간
시간은 **측정 잡음이 커서** 같은 프로그램을 n=20,000에서 5번 더 실행해 확인했습니다.

| n=20,000 (5회 실행의 범위, ms) | 시간 |
|---|---|
| Quick (Median3) | 1.07 ~ 1.26 |
| Quick (First) | 1.15 ~ 1.35 |
| Merge | 1.33 ~ 1.69 |
| Heap | 1.35 ~ 1.72 |
| Quick (Random) | 1.44 ~ 1.69 |

- **Quick(Median3)와 Quick(First)는 매번 가장 빨랐습니다.** 제자리에서 필요한 원소만 교환하고 순차 접근이라 캐시 효율이 좋습니다.
- **Merge, Heap, Quick(Random)은 범위가 서로 겹쳐서** 이 실험만으로 우열을 정하기 어렵습니다.
- 눈여겨볼 점은 **힙 정렬이 비교를 병합 정렬의 2배나 했는데도 시간은 비슷**했다는 것입니다. 정수 비교 한 번은 매우 싸서 시간을 좌우하는 것은 비교 횟수가 아니라 원소 이동과 메모리 접근이기 때문입니다. 병합 정렬은 임시 배열로의 복사(약 `2·n·log₂n`번 이동)와 `malloc`/`free`가 있고, 힙 정렬은 비교는 많지만 이동이 적습니다. 다만 힙 정렬은 부모·자식 인덱스(`i`, `2i+1`)가 멀리 떨어져 접근이 불연속적이라 캐시에 불리합니다. n=20,000(80KB)에서는 이 영향이 뚜렷하지 않았고, n이 더 커지면 힙 정렬이 불리해질 것으로 **예상**됩니다(직접 측정하지 않은 추정).
- n=1,000~2,000은 시간이 너무 짧아 잡음이 크므로(증가 배율이 4~5배로 튐) 해석에서 제외했습니다. n ≥ 4,000에서는 대체로 2배당 약 1.7~2.4배로 증가해 n log n을 따릅니다.

### 4.4 메모리 사용량
- **힙 정렬: 296 Byte로 모든 크기에서 동일**했습니다. 입력 배열 자체를 힙으로 쓰고 재귀가 없어 보조 변수와 함수 프레임 2개뿐입니다(**O(1)**).
- **병합 정렬: 크기에 비례**했습니다(5,288 → 81,768 Byte, n=20,000에서 힙 정렬의 약 276배). 임시 배열 `4n` Byte가 대부분입니다.
- **퀵 정렬: 1.8~3.8KB로 느리게 증가**(재귀 깊이 17~38에 비례, **O(log n)**). 단, 최악 입력(First + 정렬된 입력)에서는 깊이가 n이 되어 약 480KB로 폭증했습니다. 이 비율이면 n=20,000의 정렬 입력은 약 1.9MB가 되어 기본 스택(Windows 1MB)을 넘길 수 있습니다(직접 실행하지 않은 추정).
- 메모리만 보면 **힙 정렬 ≪ 퀵 정렬 ≪ 병합 정렬**이고, 최악의 경우까지 고려하면 퀵(First)이 가장 위험합니다.

### 4.5 시간·공간 복잡도 비교

| | 힙 정렬 | 병합 정렬 | 퀵 정렬 |
|---|---|---|---|
| 시간 (평균) | O(n log n) | O(n log n) | O(n log n) |
| 시간 (최악) | **O(n log n)** | **O(n log n)** | **O(n²)** (First + 정렬 입력) |
| 공간 | **O(1)** | O(n) + O(log n) 스택 | O(log n) 평균 / O(n) 최악 |
| 안정성 | 불안정 | 안정 | 불안정 |
| 입력 영향 | 거의 없음 (정렬 입력 112,126회, 무작위와 비슷한 수준) | 거의 없음 | 피벗·입력에 큰 영향 |

## 5. 결론
- **비교 횟수**: 병합 < 퀵(Median3) < 퀵(First/Random) < 힙. 힙 정렬은 sift-down에서 층마다 2번 비교해 병합 정렬의 약 2배입니다.
- **실행시간**: 퀵(Median3, First)이 가장 빨랐고, 힙·병합·퀵(Random)은 비슷했습니다. 비교 횟수만으로 속도를 예측할 수 없고 원소 이동과 메모리 접근 패턴이 중요합니다.
- **메모리**: 힙 정렬(O(1), 296 Byte)이 가장 적고 병합 정렬(O(n))이 가장 많습니다.
- 평균 속도는 **Median-of-Three 퀵 정렬**, 최악 성능 보장 + 최소 메모리는 **힙 정렬**, 최악 성능 보장 + 안정성은 **병합 정렬**(메모리 비용 있음)이 적합합니다.
